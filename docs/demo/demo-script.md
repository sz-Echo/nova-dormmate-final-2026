## 开场（0:00 - 0:03）

**画面**：深蓝色标题卡"A 组：发现异常 → 优先关注 → 开启风扇 → 验证恢复 → 事件复盘"

**解说（约 8 秒）**：
> 这是 DormMate 宿舍环境助手的最终演示，分三部分：A 组把"发现异常、处理、验证恢复、事后复盘"串成完整业务闭环；B 组把系统里的信息讲清楚；C 组用一个轻量机器学习模型，从历史数据中发现固定规则发现不了的异常。先看 A 组。

---

## A 段（0:03 - 0:47）A1-A4 业务闭环

**画面布局**：左侧 Dashboard 看板，右侧 Three.js 3D 宿舍场景，两者由同一条 MQTT 数据流实时驱动。

### 镜头 A0（0:03 - 0:08）开场：三节点实时数据

**画面**：三张宿舍卡片同时刷新（dorm-a/b/c 均为"正常"），3D 中三栋楼呈绿色状态色；顶部总览条显示"当前 3 个宿舍中，3 个正常，0 个需要关注。"

**解说（约 10 秒）**：
> 三个模拟宿舍节点通过 MQTT 实时上报温湿度。看板左侧三张卡片和右侧 3D 场景消费的是同一份数据流：卡片显示数值，3D 用楼体颜色表达状态。现在三个宿舍都正常。

### 镜头 A1（0:08 - 0:13）A1 优先关注

**画面**：dorm-b 卡片连续收到 32℃/82%、32.5℃/81%、33℃/80% 三条偏热数据；顶部红色"优先关注"横幅出现："优先关注 dorm-b：已连续偏热 5 分钟"。

**解说（约 12 秒）**：
> dorm-b 连续三条数据偏热。系统按"连续异常时长 → 异常次数 → 节点顺序"的规则程序计算，顶部横幅自动跳出——**优先关注 dorm-b**，并且给出原因：已连续偏热 5 分钟。这个判断全部由程序计算，不靠人肉盯屏。

### 镜头 A2（0:13 - 0:23）A2 处理动作（3D 联动）

**画面**：左侧选中 dorm-b，点击"开启风扇/通风"；卡片动作区变为"处理中"；右侧 3D 中 dorm-b 楼顶风扇开始旋转、窗户打开。

**解说（约 14 秒）**：
> 发现问题之后能做什么？点"开启风扇"。注意这个动作不是直接改状态——它通过一条 MQTT 动作消息发给系统：左侧卡片进入"处理中"，右侧 3D 场景同步做出反应——风扇转起来、窗户打开。用户做了什么、系统因此改变了什么，两屏完全一致。

### 镜头 A3（0:23 - 0:37）A3 恢复判断（新数据触发）

**画面**：dorm-b 收到 30℃/76%（仍偏热，"处理中"保持）→ 27℃/65% → 26℃/62%；两条正常后卡片变为"已恢复"，同时自动发布关扇动作，3D 风扇停止。

**解说（约 16 秒）**：
> 处理之后真的变好了吗？系统的回答必须由**新数据**来触发，点按钮不算。降温过程里 30 度这条仍然偏热，所以保持"处理中"、继续提示；接下来连续两条正常数据，系统才判定"已恢复"，并且**自动关扇**——右边 3D 的风扇同时停下。这里用的判定比基础规则更严格：连续两条正常才算恢复。

### 镜头 A4（0:37 - 0:47）A4 事件复盘

**画面**：左侧"今日事件"面板出现一条完整事件记录（异常开始时间、优先原因、处理动作、恢复时间、结果）；点击"导出事件"后，右侧页面切到 report.html 的"事件复盘"区，显示事件表格与程序拼接的复盘叙事。

**解说（约 15 秒）**：
> 整个过程被完整留下来：异常什么时候开始、为什么优先处理它、做了什么动作、什么时候恢复，九个字段一条事件记录。导出后进入离线分析报告，"事件复盘"区自动生成表格和一段复盘叙事——"发现 → 判断 → 处理 → 验证 → 恢复"，一条完整的故事线，全部由程序产生。

## B 段（0:50 - 1:18）B1-B4 信息闭环

**画面布局**：左侧 Dashboard，右侧当日离线报告的"今日摘要"区。

### 镜头 B1+B2（0:50 - 1:01）B1 总览成句 / B2 判断依据

**画面**：三节点正常，总览条显示"当前 3 个宿舍中，3 个正常，0 个需要关注。"；随后 dorm-c 收到 25℃/80% 偏湿数据，总览自动更新为"1 个正常，2 个需要关注……dorm-c 出现偏湿，是当前重点"，下方三张依据卡片展开：每张列出当前状态、连续异常时长、异常次数，并逐项标注"依据：……"数据来源，优先节点带 ★。

**解说（约 18 秒）**：
> 现在发生了什么？顶部总览条是一句由程序根据三个节点真实状态自动拼出的句子，不是写死的文案——dorm-c 一变偏湿，句子立刻跟着变。为什么值得关注？下面三张依据卡片回答：每项指标都注明"依据"来自哪段数据，优先节点有星标。想复核判断，直接按"依据"回数据里查。

### 镜头 B4（1:01 - 1:05）B4 合适表达：朗读提醒

**画面**：点击"朗读提醒"按钮，系统用语音朗读当前总览（视频无声，现场可听到）。

**解说（约 8 秒）**：
> 信息放在哪里合适？实时看板用眼睛看，需要听的时候点"朗读提醒"，系统把当前总览用语音读出来——听一句就能决策。3D 负责空间状态、看板负责当前重点、报告负责历史复盘，四类入口各司其职。

### 镜头 B3（1:05 - 1:18）B3 今日摘要

**画面**：右侧报告停留在"今日摘要"区——"dorm-a 全天整体正常；dorm-b 下午发生 1 次持续偏热，开启风扇后 20 分钟恢复；dorm-c 晚间出现 1 次偏湿，目前仍未恢复。今日共发生 2 次需要关注的环境事件。"

**解说（约 12 秒）**：
> 今天发生了什么？右边是系统自动生成的今日摘要：谁出了问题、做了什么、结果如何，三句话讲完一天。这份摘要由程序读取当天数据和事件记录生成，换一份数据重新运行，摘要就重新生成——所以它是真实数据的结果，不是预先写好的总结。

## C 段（1:21 - 2:09）C1-C4 轻量 ML 闭环

**画面布局**：左侧 report.html 的"ML 异常分析"区，右侧依次切换：模型控制台输出 → 对照结果 JSON → 两份 CSV → README 说明。

### 镜头 C3（1:21 - 1:27）C3 结果接回报告

**画面**：报告顶部"ML 异常分析（C3）"区——8 组数据三列并排：当前值 / 固定规则 / ML 判断，其中 3 行橙色高亮，如"dorm-a | 29℃/72% | 固定规则：正常 | ML：与历史明显不同"（分数 0.6738）。

**解说（约 15 秒）**：
> 机器学习的结果没有停在 Python 脚本里，而是接回了 DormMate 的报告。左边这张表把固定规则和 ML 判断并排对照：比如 29 度、72% 湿度，固定规则判"正常"——没到 30 度也没到 75%，但 ML 认为它"与该宿舍历史明显不同"，因为 dorm-a 平时一直在 24 到 26 度、55% 到 65% 之间。规则没发现的偏差，模型从历史里发现了。

### 镜头 C2（1:27 - 1:39）C2 对照与结果保留

**画面**：右侧显示 `analysis/c_ml.py` 的真实控制台输出——100 棵隔离树、8 组对照表、结尾"发现 3 组'固定规则正常、ML 明显不同'"；随后切换到 c_compare.json（浏览器原生 JSON 视图）。

**解说（约 15 秒）**：
> 右边是模型脚本的真实运行输出：用 dorm-a 的 40 条历史数据训练隔离森林，再对 8 组新数据做判断，对照表最后明确报告"发现 3 组规则正常、ML 明显不同"。所有对照结果存成 JSON 文件保留。这个模型是自实现的轻量隔离森林，因为本机 Python 版本装不上 sklearn，替代原因在 README 里有完整记录——按任务书的等价替代先例处理。

### 镜头 C1（1:39 - 1:47）C1 数据分离

**画面**：右侧先显示 c_new.csv（8 组待判断新数据，2026-09-28），再显示 c_history.csv（40 条历史，2026-09-26/27）——两份文件时间零重叠。

**解说（约 12 秒）**：
> 模型是怎么学会"平时"的？两份数据严格分开：历史是 26、27 号两天的 40 条模拟记录，待判断的新数据是 28 号的 8 组——新数据绝不混进历史再判断自己。固定随机种子 42，任何时候重跑，结果完全可复现。

### 镜头 C4（1:47 - 2:09）C4 不理想案例

**画面**：右侧显示 README 中"C 组轻量 ML"与"已知限制"段落——27.5℃/70% 的案例说明（规则正常、ML 明显不同，分数 0.6738 比三组规则异常还高）及原因分析。

**解说（约 16 秒）**：
> 最后是闭环要求的自省：模型也会判断不好。这里主动保留了 27.5 度、70% 这个例子——现实中只是略偏热偏湿，规则判正常，但模型给它的异常分数比真正的规则异常还要高。原因很清楚：历史数据只有 40 条，而且全都挤在 24 到 26 度、55% 到 65% 的窄区间里，模型学到的"常态"边界太窄。C 组明确不做标签、训练集划分、Accuracy、F1 这些正式指标，跑通"数据 → 模型 → 应用 → 说明"的轻量闭环就算完成。
